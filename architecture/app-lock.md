# App Lock (`AppLock/`) — free

*Part of the Emojily architecture reference. Up: [OVERVIEW.md](../../OVERVIEW.md) · Index: [§6 Features](../../OVERVIEW.md#6-features)*

---


Face ID / Touch ID / passcode in front of the journal, stored in `settings.appLockEnabled`. Free by
design: it is a trust signal for a private journal, not a paywall lever.

- **`AppLockService`** wraps `LAContext` with `.deviceOwnerAuthentication` (not `...WithBiometrics`), so the system passcode is offered whenever biometrics fail or aren't enrolled. `AppLockBiometryKind.current` reports what to *draw* (Face ID / Touch ID / Optic ID / padlock), which is separate from whether a lock can run at all.
- **`AppLockViewModel`** owns the lock. It locks on a true `.background` transition only — `.inactive` (a system sheet, Control Center, the authentication prompt itself) must not re-lock, or authenticating would fight itself. A non-interactive `AppLockPrivacyCoverView` covers `.inactive` so a reflection stays off the app-switcher snapshot — a `.thickMaterial` blur rather than an opaque card, so the snapshot still reads as Emojily while nothing on it stays legible.
- **The prompt is automatic**, once per lock: cold launch fires it from the lock screen's `onAppear`, a foreground return fires it from the `.active` scene phase. Evaluating from the background is skipped — it shows the user nothing and would burn the prompt. A cancelled prompt does *not* re-arm when the scene settles; the Unlock button is the retry.
- **Unlock is animated** by the shared `AppLockGlyphView` (`SharedUI/`): its authentication ring sweeps while a prompt is active, then the biometry glyph flips to an open padlock, the halo goes green, and a ring ripples out before the lock screen leaves. The lock screen holds for `unlockAnimationDuration` (560 ms) to let it play, and skips nonessential motion entirely under Reduce Motion.
- **VoiceOver stops at the lock screen.** `AppLockView` is a modal accessibility container, so while it is up nothing behind it can be reached. The app root does not hide itself: it used to, with `.accessibilityHidden(isLocked)`, but that is `false` whenever the app is unlocked, and `false` is not neutral — it re-exposed decorations hidden beneath it, and the audit met saved Today's mood wash as a nameless full-screen element — on the screenshot scenario, drawn straight under the root; inside a `TabView`, as the app draws it, it audited clean. `.accessibilityHidden(while:)` is no answer at the root either, since it would rebuild the whole app on every lock and unlock. `AccessibilityAuditTests.testLockHidesTheScreenBehindIt` holds the line: saved Today behind a lock that never opens (`EVERYDAYEMOJI_SCREENSHOT_LOCKED`, debug only) must expose none of the labels it exposes unlocked. With the root's hide simply deleted and no modal, it fails and lists the whole screen, note included. It reads the tree through XCUITest's queries, which honour the modal the way VoiceOver is documented to; Apple's audit does not — it still walks the covered screen, reporting its text as failing contrast — so the audit is no evidence here either way. Nobody has checked it with VoiceOver itself; that is on B-29.
- **The privacy cover stays silent.** It is up only while the scene is `.inactive`, when whatever is in front of the app — Control Center, the app switcher, a system alert — holds VoiceOver's focus, so it is hidden rather than modal. The root never hid the app in that state either.
- **`AppLockActivationService`** owns the one rule both entry points share: the preference only flips after the user proves *right then* that they can pass the lock. Turning it **on** prompts first, so nobody discovers at the next launch that their face doesn't open it; turning it **off** prompts too, so an unattended unlocked phone can't strip the lock off a private journal. A device with no passcode reports `.unavailable` and the toggle stays off with an explanation; if the passcode is removed *after* App Lock was on, disabling skips the prompt rather than stranding the setting on forever.
- **Entry point:** the Settings row via `AppLockSettingsViewModel`, which snaps the toggle back when a prompt is refused. App Lock is intentionally deferred from onboarding until after the user has experienced the journal.
- **Never a lockout:** no passcode enrolled, or the setting turned off while locked, unlocks rather than trapping the user.
